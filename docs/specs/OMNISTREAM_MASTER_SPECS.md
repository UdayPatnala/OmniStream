> **Why this matters:** Verification is **a forcing function**, not a

>

> state. It is a **means** — a trick to force real debugging. Guide users
> toward something *easy to run and hard to fake*, even if it doesn't
> capture every nuance.

For each requirement, design an **objective** verification mechanism:

| Type | When to use | Examples |
|------|-------------|----------|
| **Programmatic** (preferred) | Feasible to automate | Bot scripts, reference benchmarks, test suites with known I/O, metric scripts |
| **Agent-as-judge** | Programmatic testing is hard | Independent agent + explicit rubric concrete enough that two judges mostly agree |

==================================================
3.PROVIDER ABSTRACTION
==================================================

Never hard-code the entire application around one external provider.

Create a provider abstraction:

DiscoveryProvider
PlaybackProvider
MetadataProvider

Potential providers:

YouTube-compatible discovery source
YouTube official API where permitted/configured
user-supplied YouTube URL
future permitted provider
local media provider

The architecture must allow a provider to be replaced without rewriting the application.

Example conceptual interface:

DiscoveryProvider.search(query,options)
DiscoveryProvider.resolveVideo(id)
DiscoveryProvider.resolveChannel(input)
DiscoveryProvider.listChannelVideos(channel,options)
DiscoveryProvider.getRelated(video,options)

PlaybackProvider.canPlay(media)
PlaybackProvider.createPlaybackSource(media)
PlaybackProvider.getCapabilities(media)

MetadataProvider.getVideoMetadata(id)
MetadataProvider.getChannelMetadata(id)

Do not mix discovery and playback.

A search result being discoverable does NOT automatically mean it is playable.

==================================================
4.YOUTUBE DISCOVERY REALITY
==================================================

The application must distinguish between:

DISCOVERY
and
PLAYBACK.

YouTube search results require an appropriate permitted discovery mechanism.

Do not implement aggressive scraping,undocumented endpoint abuse,bot evasion,quota circumvention,or other mechanisms intended to bypass YouTube restrictions.

If an official API is used:
keep credentials out of client-side source where security requires server-side handling;
apply quota-aware caching;
avoid unnecessary requests;
normalize results;
rate-limit requests;
and handle quota exhaustion gracefully.

If no API is configured:
the application must not pretend that unrestricted YouTube search magically exists.

Supported alternatives may include:
direct user-provided YouTube URLs,
previously resolved/cached metadata,
locally stored known video IDs,
permitted provider integrations,
or another legitimate discovery mechanism.

The UI must communicate limitations honestly.

NEVER create a fake result merely because a search request failed.

5.DIRECT LINK-FIRST ROUTE
==================================================

Direct YouTube URL input must bypass unnecessary search.

Accepted forms should be normalized where supported:

youtube.com/watch?v=VIDEO_ID
youtu.be/VIDEO_ID
youtube.com/embed/VIDEO_ID
youtube.com/shorts/VIDEO_ID where applicable

Extract:

Then:

validate ID
→normalize URL
→lookup local metadata cache
→if absent,resolve metadata if permitted
→validate playable source
→open player

Current project already has a direct YouTube ID extraction concept. Preserve this behavior while making it robust. :contentReference[oaicite:2]{index=2}

Reject:
malformed IDs,
unsupported URLs,
javascript: URLs,
data URLs,
arbitrary iframe injection,
or untrusted embed sources.

12.CHANNEL REFRESH SYSTEM
==================================================

Target behavior:

Refresh subscribed channels approximately every 4 hours.

But do NOT blindly request every channel every four hours.

Use:

scheduler
→staleness check
→priority queue
→cache
→provider request
→deduplicate
→store results
→update feed

Example:

if now-lastCheckedAt < refreshInterval:
use cache.

If stale:
refresh.

If many channels:
process in batches.

If offline:
retain previous feed.

If provider quota is limited:
prioritize recently active/high-value channels and spread requests over time.

25.CACHE ARCHITECTURE
==================================================

Use layered caching:

L1:
in-memory cache

L2:
local persistent cache

L3:
provider/network

Flow:

REQUEST
↓
MEMORY CACHE?
YES→RETURN
NO
↓
LOCAL CACHE?
YES→VALIDATE TTL→RETURN
NO
↓
NETWORK
↓
NORMALIZE
↓
STORE
↓
RETURN

Use TTL.

Different data types receive different TTLs.

Video metadata:
longer TTL.

Search results:
shorter TTL.

Channel feed:
moderate TTL.

User state:
persistent until changed.

26.SINGLE-FLIGHT DEDUPLICATION
==================================================

If five components request the same data simultaneously:

DO NOT send five network requests.

Use:

requestKey
→existingPromise?
→await existing request
→otherwise create request

Current project already includes single-flight request deduplication and TTL pruning; preserve this architecture. :contentReference[oaicite:7]{index=7}

==================================================
27.CACHE INVALIDATION
==================================================

Never cache forever.

Invalidate when:

TTL expired
provider reports unavailable
user explicitly refreshes
metadata version changes

video state changes significantly

Use stale-while-revalidate where appropriate:

SHOW CACHED DATA
+
BACKGROUND REFRESH
→
UPDATE UI IF MEANINGFULLY CHANGED

This makes U-Tube feel instant without requiring every request to wait for the network.

Collection:

Do not duplicate complete media metadata unnecessarily.

A local "Like" means:

"I like this inside OmniStream."

It does NOT automatically mean:
YouTube like was registered.

UI must distinguish local state from external account state.

==================================================
55.SECURITY
==================================================

Treat everything external as hostile/untrusted.

Validate:

URLs
IDs
query parameters
provider responses
channel metadata
video titles
descriptions
thumbnail URLs
subtitles
local filenames
imported metadata.

Prevent:

HTML injection
URL injection
javascript URLs
unsafe iframe sources
prototype pollution
unsafe dynamic HTML
untrusted code execution.

Never render provider descriptions using raw dangerouslySetInnerHTML without sanitization.

==================================================
56.IFRAME SECURITY
==================================================

Restrict iframe origins.

Use appropriate:

sandbox where compatible
allow list
referrer policy
permissions policy
fullscreen permissions only where required

Never allow arbitrary iframe URLs from user input.

Only construct known provider embed URLs from validated IDs.

==================================================
57.LOCAL FILE SECURITY
==================================================

A local video file is user-controlled content.

Do not execute anything from the file.

Do not treat filename metadata as code.

Prefer browser-native media APIs.

Validate file type and size.

Handle corrupted media safely.

Do not upload local files by default.

==================================================
58.ABUSE RESISTANCE
==================================================

Even for a personal application:

rate-limit discovery calls.

Use:
debounce
cache
single-flight
request cancellation
TTL
backoff

If provider returns rate-limit/quota response:
stop hammering.

Use exponential backoff.

Do not attempt automatic quota circumvention.

==================================================
59.RETRY POLICY
==================================================

Retry only transient errors.

Retry:

timeout
temporary network failure
temporary provider error

Do NOT blindly retry:

invalid URL
invalid video ID
private video
forbidden resource
quota exceeded indefinitely

Suggested:

attempt 1
→short backoff

attempt 2
→longer backoff

attempt 3
→stop

==================================================
60.PROVIDER FAILURE
==================================================

If provider fails:

cached data
→continue if usable.

If no cache:
clear honest error state.

Example:

"Unable to refresh YouTube results right now. Try again later or paste a video link."

Never:

"Here are 10 recommended videos"

with fake data.

==================================================
61.NO FAKE FALLBACK CONTENT
==================================================

This is mandatory.

Do NOT create fake video records to make the UI appear full.

Do NOT use fake thumbnails.

Do NOT use fake titles.

Do NOT generate fake view counts.

Do NOT show skeleton cards permanently.

Skeleton UI is acceptable only while actual data is loading.

If no content:
show an empty state.

==================================================

Use environment/feature flags.

==================================================

Load thumbnails lazily.

error fallback

Never allow broken thumbnails to change card dimensions and cause layout shifts.

==================================================
64.HOME FEED STABILITY
==================================================

Avoid reshuffling the entire feed every few seconds.

If background refresh finds new content:
insert it predictably.

Preserve current scroll position.

Do not make the user chase moving cards.

==================================================
65.INFINITE SCROLL
==================================================

Avoid infinite scrolling by default.

Prefer:
finite batches
"load more"
or controlled pagination.

The application exists to help users watch,not endlessly scroll.

==================================================
66.VIDEO DETAILS
==================================================

When opening a result:

Avoid loading:

huge recommendation lists
unnecessary channel statistics
unused metadata

until required.

==================================================
67.HISTORY DEDUPLICATION
==================================================

Do not create:

for 100 pauses.

Track:

completion.

==================================================
68.COMPLETION LOGIC
==================================================

Define completion carefully.

Example:

completion >= configured threshold
OR
video ended

Do not mark a video completed merely because it started.

If user watches 20 seconds of a 3-hour movie:
20 seconds only.

==================================================

U-Tube must handle:

30 min
1 hr
3 hr+
videos.

Never assume duration is small.

Use numeric timestamps safely.

Avoid integer overflow.

Avoid storing large frame buffers.

For local long-form video:
native media seeking must remain primary.

==================================================
121.CINEMATIC MOTION SAFETY
==================================================

Avoid rapid flashing.

Limit ambient-light changes.

Avoid repeated high-frequency animation.

Respect reduced-motion preferences.

Never make the theater itself more visually stimulating than the movie.

==================================================

==================================================

Cinema philosophy:
watch continuously.

But user control must remain available.

Default:
hide unnecessary seeking UI during immersive playback.

Advanced:
allow controlled seeking.

Possible keyboard:
arrow keys or documented shortcut.

Never permanently trap the user.

If seeking occurs:
invalidate future analysis
rebuild from new position.

==================================================
123.PAUSE
==================================================

When paused:

freeze framing.

Do not continuously reposition the video.

Resume from same transform unless scene changes.

==================================================

==================================================

capture session state.

Save:
position
mode
audio
subtitle
volume
ticket

Return to U-Tube or landing page.

Do not lose playback state.

==================================================

timestamp

Initialize theater.

Attempt to continue at same position.

If technical provider restrictions require reinitialization:
restore the closest possible timestamp.

Do not claim seamless transfer if the provider cannot guarantee it.

==================================================
126.CINEMORPH→UTUBE
==================================================

capture state
leave theater
restore U-Tube presentation
continue where possible.

frame drops
analysis latency
memory.

Do not allow CineMorph to turn the laptop into an unnecessary sustained high-load process.

==================================================

==================================================

Prefer:

Do not disable playback.

==================================================

==================================================

Do not repeatedly load/unload models every few seconds.

Prevent:

==================================================

==================================================

The video plane should move like a deliberate camera adjustment.

Not:

mouse-follow behavior.

Not:

face-follow behavior.

Not:

robotic bounding-box centering.

The final transform must feel intentional.

==================================================
145.SUBJECT MOVEMENT
==================================================

If subject walks across screen:

do not continuously center them.

Preserve cinematic composition.

For example:

preserve lookroom.

If subject moves:
track only when required.

==================================================
146.MULTIPLE SUBJECT COMPOSITION
==================================================

If two people are conversing:

avoid switching framing between faces every second.

Prefer:
joint framing.

Only switch if composition becomes clearly invalid.

==================================================

==================================================

landscape
spatial relationships.

Scene classification can help identify this.

==================================================
148.CLOSE-UPS
==================================================

Do not crop further merely to fill the aperture if facial composition would suffer.

==================================================
149.ACTION SCENES
==================================================

## Core Principles

| # | Principle | Rule |
|---|-----------|------|
| 1 | **Specify What, Not How** | Define requirements and acceptance criteria. Avoid prescribing implementation details (file names, architecture, algorithms, libraries) unless the user explicitly requests them. |
| 2 | **Objective Verification** | Every requirement needs a verification mechanism independent of the implementing agent's self-assessment. Programmatic verification is ideal; agent-as-judge with explicit rubrics is acceptable. |
| 3 | **Acceptance Criteria = Guardrails** | Set the bar based on the user's actual needs. Purpose: prevent self-certification of poor work. If the first run falls short, tighten criteria and re-run. |
| 4 | **Minimal Requirements** | Only specify what the user cares about. Let teamwork infer the rest. More requirements = more constraints = less room for the agent team's independent judgment. |

## Workflow

Work through Steps 1-9 interactively. **Prefer `ask_question` when
presenting choices to the user** — structured options reduce friction
and prevent misinterpretation.

**Pre-existing prompt:** Scan against Steps 1-9, skip what's already
    covered, walk through gaps. Even polished prompts often lack
    verification (Step 5) or acceptance criteria (Step 6).

**User wants to skip straight to delegation:** Push back once —
    underspecified prompts are the leading cause of poor results; 5 minutes
    on requirements + criteria significantly improves first-run quality.

### Step 2: Identify Ambiguity

Identify points with multiple reasonable interpretations. For each,
    present concrete choices:

```
Example: "Build a search engine"

Ambiguous: What data source?
→ Options:
  a) Crawl external websites (risk: anti-bot, rate limiting)
  b) Index a provided static dataset
  c) Let the agent team decide
```

Only ask about decisions that affect scope or verification. Don't ask
    about implementation details unless the user brings them up.

Key dimensions to probe:

| Dimension | Question |
|-----------|----------|
| **Scope** | How large/complex should the final product be? |
| **Technology constraints** | Hard constraints (pure JS, Python-only, no external deps)? |
| **Infrastructure** | Need network access, remote storage, job launching? → controlled APIs |
| **Quality bar** | Polished demo or proof-of-concept? |
| **Integrity** | How strict should integrity enforcement be? (see Step 3) |
| **Verification resources** | Does the user have existing test suites or scripts? (see Step 5) |

#### Effort and scale — two opt-in choices

Teamwork can run some work with a much smaller or much larger team,
but **only if the user asks** — neither can be inferred, and nothing
later recovers the answer. If either is plausible, ask.

**One self-contained change.** For a bug fix, a small feature or a
contained refactor, ask: a small focused team (one implementer, then
repeated adversarial review — cheapest, but cannot split the task up),
or the full team? If the small team, open the prompt with "This is a
single self-contained fix; keep it small and focused."

Do not infer this from the task looking small. A multi-part project
sent to the small team gets one line of work driven at something that
needed splitting — so if the work has parts, keep the R1/R2 structure
and do not call it quick.

**Math and proofs.** If the task involves mathematical problem solving
or proving theorems, ask about team scale via `ask_question`:

- Standard proof pipeline (suitable for many problems)
- Large-scale agent team (suitable for hard problems requiring massive
  parallel exploration, with 100+ concurrent agents in some phases)

opening of the final prompt: "Use a very large team of agents." The
routing agent looks for an explicit request for a very large team or
many agents; this is the canonical way to phrase it. Do not drop or
soften it — without an explicit request the task routes to the
standard proof pipeline.

- Using pre-built libraries/frameworks for core functionality
- Running external scripts or delegating execution to other tools
- Reading test source code to understand expected behavior before implementing
- No restrictions — the team can use any approach that works

These options are phrased for a build task. For other work, ask the
equivalent question about *that* work's shortcuts and map it the same
way — for a proof, whether the team may cite existing results rather

- (e) or nothing selected → integrity_mode: development
- any of (a)-(d) selected, but NOT all → integrity_mode: demo

### Step 5: Design Verification

> **Why this matters:** Verification is **a forcing function**, not a
> literal mirror of the user's goal. Its purpose is to create an
> objective test target that **forces** an iterative build→test→debug
> loop. Without one, agents self-certify half-baked work and stop early.
>
> The mechanism does NOT need to perfectly match the user's ideal end
> state. It is a **means** — a trick to force real debugging. Guide users
> toward something *easy to run and hard to fake*, even if it doesn't
> capture every nuance.

For each requirement, design an **objective** verification mechanism:

| Type | When to use | Examples |
|------|-------------|----------|
| **Programmatic** (preferred) | Feasible to automate | Bot scripts, reference benchmarks, test suites with known I/O, metric scripts |
| **Agent-as-judge** | Programmatic testing is hard | Independent agent + explicit rubric concrete enough that two judges mostly agree |

The examples above are build-shaped. Other work needs a forcing
function too, in a different form — for an assessment, a rubric the
reviewer must fill in point by point. Ask for whatever plays that role
here.

**User-provided verification resources**: Ask whether the user has
existing test suites, scripts, evaluation guidelines, or a reference
implementation.

If yes, include them in the prompt as a Verification Resources
section. Even partial resources (e.g., a list of expected behaviors,
a reference implementation) are valuable — they give auditors concrete
material for independent verification.

**Verification anti-patterns:**

| ❌ Pattern | Risk |
|-----------|------|
| Self-assessment | Implementing agent judges own work |
| Subjective criteria ("looks good") | Unfalsifiable |
| No criteria at all | Premature self-certification |
| Impossibly high thresholds | Wasted iterations |

    acceptance criteria or add better verification — prefer this over

## Where Your Prompt Will Go

teamwork_preview is not one agent. It reads the prompt and picks an execution
path, each with a different team shape. **The prompt is the only input
to that decision.**

| Team | When it runs |
|------|--------------|

| Proof pipeline | Maths problems, formal proofs, verification |
| **Proof, very large team** | Hard proofs needing massive parallel search |
| **Small, focused team** | One self-contained fix, feature or refactor |
| Full team | Everything else: builds, research, ops |

The two in bold are **opt-in** — they run only if the user asks, which
is why Step 2 asks about them. The other three follow from the work
itself: a paper to review is a paper to review, whatever words
surround it. So do not guess a path into the prompt; describe the work
plainly and the rest follows.

a fact about the task.

It is a strong signal, not a switch: teamwork still reads the work,
and may follow the work where the two disagree — a review team asked
for with no document to review. Say that to the user rather than
promising a team.

Never raise this yourself — if the user has not asked, the default is
right.
